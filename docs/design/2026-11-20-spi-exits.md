# Why a node that missed a commit may not repair: the exits

Status: investigation notes · 2026-11-20 · found with `tests/network/faults.ts` (scenarios 2 and 3)

## Symptom

A node is crashed (or frozen) while transactions commit, and restarted. After
one more transaction per stream, some streams on that node stay at their old
revision (`n3=1-...` while the other three nodes are on `3-...`). The same
happens on 5.7.2, so it is not from the neighbourhood redesign. With debug
logging on, the failure rate changes (it is timing dependent); runs of
scenario 2 left 3 to 12 of 24 streams behind, and scenario 3 failed in about
one run in three.

## How a non-origin node is meant to repair (SPI, `Endpoints.InternalInitalise`)

A transaction reaches this node as a broadcast. The worker runs it and votes
no with `Input Stream Position Incorrect` (the node holds an older revision).
The other nodes commit. The host then evaluates, for this node's entry
`$nodes[self].error`, whether to adopt the network's revision of the streams
(`SPI NON Origin - Must Check`, ask every node for the `:stream` docs, take
the majority, rewrite, then walk the umid history back).

## What was found

1. **The check is driven by incoming peer frames, not by this node's own
   failure.** In `Host.pending()` the first frame of an internal `$broadcast`
   transaction sets `responded = true` and resolves its promise at once with
   `{ ok: true }`. The worker's later `commited`/`failed` result is then
   ignored (`resolve` is guarded by `!responded`), so the SPI block in the
   first call never sees this node's error. Every later frame for the same umid
   resolves immediately with the pending entry as it is at that moment. SPI
   runs only if one of those frames arrives after the worker's error has been
   merged into the pending entry. If all the peers' frames arrive before this
   node finishes failing, nothing triggers SPI. (Debug run: 17 transactions
   failed on the crashed node, 8 reached `SPI NON Origin - Must Check` and
   repaired their streams, 9 never reached the check and those 7 streams
   stayed behind.) This is the main exit.
2. **`SPI Skipped not enough returned for consensus yet`** (`tmp()` in the
   same block) returns without retrying. The code has a comment, "Maybe retry
   tmp somehow? They could be spi lock failures". Not seen in these runs, but
   it is the same shape of silent exit.
3. **Abstention on a partial sample** (`Endpoints.spiConsensus`, logged as
   `SPI NOWINNER`): a stream some node could not report (for example locked by
   a transaction in flight) is not decided and not retried. Correct to abstain;
   there is no later attempt.
4. **The `rewrote` cache (500 ms) is keyed by umid and by document id.** A
   second transaction for the same stream inside that window is skipped.
5. **The worker's own delay**: a failed vote with consensus still possible
   holds `failed` for up to 10 s (`willEmit`), and `Process.failed()` in
   `network/process.ts` overwrites `$nodes[self].error` with the text of the
   failure it reports. Neither blocked repair in the runs here, but both sit
   on the same path.
6. **Nothing else repairs it.** The interagent logs `left for SPI`, so a
   stream that SPI did not repair stays behind until something touches it,
   and the next transaction can hit exit 1 again.

## Cheap prevention vs reaction

- Exit 1 can be closed at the source: when the host receives the worker's
  failure report for an internal broadcast transaction (`case "commited"` after
  the nodes are merged) and this node's error is a position or not-found error,
  run the same SPI check once for that umid. It adds no traffic and no timer,
  and only fires for failed-position transactions.
- Exit 2 can get one bounded retry.
- Exits 3 and 4 are by design; a catch-up (ask the neighbours for the umids
  committed since this node's newest, adopt the tip and walk back) covers them
  and the idle case where nothing touches the stream again.

## Evidence

`tests/network/faults.ts` now prints each node's revision for a stream that
fails to converge, and with `FAULT_LOGS=<dir>` keeps the node logs.
`FAULT_DEBUG=1` turns debug logging on.
