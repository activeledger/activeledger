# Catch-up: a node that missed commits finds them itself

Status: draft for review · 2026-11-20

## Goal

A node that was down, frozen, partitioned or started late ends up on the same
revision of every stream as the rest of the network, without waiting for a
transaction to touch each stream, and without a full restore.

Not in scope: the consensus protocol, votes, build gating (nothing here changes
what a vote means or what is stored), and a long outage (a gap larger than a
set cap is handed to the restore tool, as the SPI walk already does).

## Problem

Today a node that missed a commit repairs a stream only reactively: the next
transaction that touches it fails with "Position Incorrect", and the inline
self repair (SPI) adopts the network's revision. That has several silent exits
(`2026-11-20-spi-exits.md`), and one gap no fix to it can close: a stream that
nothing touches again stays behind for ever. The soak and the fault suite both
show it:

- a node started late misses a transaction that commits before it is noticed
  (the soak found this in up to 12 of 60 runs before the retry fix);
- a node crashed mid-flight and restarted keeps 3 to 12 of 24 streams at their
  old revision until something writes to them (`faults.ts`, scenarios 2 and 3).

## Idea

Pull, in reverse, the way SPI already works. Ask the neighbours what was
committed after what this node last has, adopt the tip of each affected stream
once (SPI), then walk the umid history back until a umid already held. Never
replay transactions or their state.

## What already exists (checked in the code)

| Piece | Where | Use here |
|---|---|---|
| Umid index: one row per committed umid, key `umid:<time>,<umid>`, time is when **that node** wrote it | events database, read through the local storage route `GET /activeledgerevents/umids?from=&limit=` (`selfhost.ts`) | the list of "what did you commit since". Local only today |
| Fetch a umid document from the neighbours | `knockAll("umid/<id>")`, `Sync.backfillUmid` | adopt a missed umid and replay its events |
| Network's current copy of streams | `knockAll("stream", { $streams })`: returns the stream and `:stream` docs, and reports a stream held by a transaction as unavailable | the tip of each stream |
| Majority tally | `Sync.spiConsensus` (abstains on a partial sample, reports forks) | decide the tip safely |
| Walk history back | `Sync.walkUmidHistory` (follows `prev` per stream, stops at a umid already held, cap 100) | fill in the umids behind the tip |
| Rewrite a stream at a revision | `bulkDocs(..., { new_edits: true, force_rev })` as in SPI #2 | adopt the tip |
| Stream lock | `Locker.hold / release` (host) | stop a live transaction racing the rewrite |
| Revision order | `Sync.revPosition`, `SPI_FORK` | never move a stream backwards; report a fork |

New: one read-only node-to-node endpoint, and the orchestration class.

## Proposal

### 1. `GET /a/umids/<from>?limit=<n>` (new, node to node)

Returns `{ rows: [{ umid, timestamp }], more: boolean }` from this node's umid
index, oldest first, at most `limit` (default and maximum 500). Only answered to
a configured neighbour's address (the same firewall check as `/a/all`); anyone
else gets 403. An older node answers 404, and catch-up simply skips it. It is a
range scan on an index that already exists, so it is cheap.

### 2. A `Catchup` class, with injected peers, store, locker and clock

Like `Pairing`, in its own file with a small interface for everything outside
(`umidsSince(peer, from)`, `streams(ids)`, `umid(id)`, `store`, `lock`, `now`),
so the algorithm is tested without a network.

One run:

1. **From** = the cursor (below), minus a margin.
2. Ask one neighbour (the first home neighbour that answers, others as
   fallback) for rows from there, in pages. For each row, if the umid is held
   locally, skip it (one local read). Collect the rest, up to a cap per run
   (default 5,000). If the cap is hit, log that a full restore is the right tool
   and carry on with what was collected.
3. Fetch each missing umid document (`backfillUmid`, which also replays its
   events). From it, read the streams it updated and their `prev`. Group by
   stream: **the work is per stream, not per umid**.
4. For each affected stream: ask the neighbourhood for the stream and `:stream`
   docs, tally with `spiConsensus`. If it abstains (a node could not report, or
   the stream is locked by a transaction), leave the stream for the next run.
5. If the winning revision is ahead of the local one (`revPosition`): hold the
   stream lock, rewrite at the winning revision, release. If it is equal in
   position but different (a fork), do nothing and log `SPI_FORK`. If the local
   one is ahead, do nothing.
6. `walkUmidHistory` from the winning umid, to fill in the umids behind the
   tip. It stops at the first one already held.
7. Advance the cursor to the newest timestamp of the page processed, only when
   every stream in it was handled or deliberately skipped (a fork). A stream that
   abstained keeps the cursor where it was, so the next run sees it again.

N missed commits on one stream cost one rewrite and N umid documents, not N
replays.

### 3. The cursor

The index rows this node writes are stamped with the time **it** writes them,
and an adopted umid is written now. So this node's own newest row is not "how far
I have caught up": after one catch-up it would jump to the present and hide
everything still unprocessed. The cursor is therefore stored: the newest
timestamp, in the serving neighbour's clock, up to which every stream was
settled. First run (no cursor): this node's newest row from live processing is
not distinguishable, so use the time the node last stopped (the newest row
written before this process started, found by reading the index backwards from
the process start time). Clocks differ by milliseconds, so the margin is small
(default 2 s) and a held umid costs one read.

Where the cursor lives is an open question (below).

### 4. When it runs

- Once, after start, when the quorum is reached (`Host.quorum()`), or after the
  30 s fallback.
- When this node regains the quorum after losing it (frozen, partitioned): a
  transition of `Host.quorum().reached` from false to true.
- A slow backstop, once every 10 minutes with jitter: one request, `limit=1`,
  to one neighbour, "anything after my cursor?". If not, nothing else happens.
  This catches a node that drifted without noticing (a dropped frame that the
  resend did not recover).
- Never concurrently with itself, and never when fewer than the quorum are home.

### 5. Safety

- Only a majority-agreed revision is adopted (`spiConsensus`).
- A stream is rewritten only while holding its lock, so a live transaction waits
  in the queue and sees the adopted revision. If the lock is busy the stream waits
  for the next run (no spinning).
- Never moves a stream backwards or over a fork.
- Bounded: pages of 500, a cap per run, concurrency of 4 streams, the existing
  50 ms hop delay, so it cannot starve live traffic. Off with `catchUp: false`.
- Idempotent: running it twice does nothing the second time. It can be
  interrupted at any point: what was adopted stays, and the cursor only moves
  after a settled page.

### 6. Cost

In sync: on a trigger, one `umids` request to one neighbour returning rows the node
already holds (one local read each); the backstop is one request with `limit=1`.
Behind: bounded by the gap, one `stream` request and one rewrite per affected
stream, one umid fetch per missed umid. Memory: one page of rows and one map of
streams per run, capped.

## Compatibility

- No `build` gate: it sends read-only requests that every node can answer and
  writes only what SPI already writes.
- A mixed network works: an older neighbour answers 404 to `/a/umids`, and
  catch-up uses another; if none answers it does nothing. Old nodes need no
  change to be caught up from.
- Hybrid nodes have their own sync and are not touched.

## Tests

- Unit (`Catchup`, fake peers and clock): one stream missed several commits (one
  rewrite, umids walked back); several streams; already in sync (no writes);
  a held umid skipped; majority disagrees (abstain, retried next run); a locked
  stream (skipped, cursor held); a fork (untouched, logged); local ahead
  (untouched); cap exceeded (partial, logged); cursor advance and resume after an
  interruption; two runs in a row.
- Endpoint: firewall, paging, `limit` cap, older node 404.
- Live (`tests/network`): the faults scenarios 2 and 3 with the node restarted and
  **no** further traffic converging within a bound; a node frozen and thawed with
  no traffic; the staggered soak with the retry fix off, expecting no lag.

## Phasing

1. The endpoint and the `Catchup` class with its unit tests, off by default.
2. The triggers, the cursor and the live tests, then on by default after a soak.

## Open questions

- Where the cursor is stored: a document in the events database
  (`catchup:cursor`) keeps it with the index and survives restarts, but is a
  second kind of document in a database whose ids are otherwise `umid:...`.
- How many neighbours to ask for the umid list. One is enough for the list (each
  stream's state is then decided by a majority), but a neighbour that is itself
  behind lists less; asking two and merging is cheap.
- The cap per run and the margin; both are guesses until a soak shows real gaps.
- Whether a neighbour that becomes home should also be offered a push ("I hold
  umids after your cursor") so a late joiner is caught up without waiting for its
  own trigger. The pull from the late joiner already covers it, so not proposed.
